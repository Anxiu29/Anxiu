# 架构优化状态与停止条件

## 当前结构

```text
UI（Vue / Pinia）
  -> KeyboardDriverService
  -> DeviceSession
  -> SaveConfiguration
  -> KeyboardDevice 能力端口
  -> C98Driver 组合适配器
       -> CapabilityDescriptor
       -> 设备物理矩阵数据
       -> KeyCatalog
       -> XsydKeyboardProtocol
            -> XsydCommandClient
            -> commands / codec
            -> DeviceTransport
                 -> WebHidTransport
```

## 已经稳定的替换边界

| 变化 | 应新增或替换 | 不应修改 |
| --- | --- | --- |
| 更换 Vue | 新 UI 适配器 | domain、application、protocol |
| 增加键盘型号 | `devices/<model>` 驱动、矩阵、能力和对应 UI 几何 | 保存用例、协议命令 |
| 同型号不同固件能力 | `CapabilityDescriptor` 变体 | 协议流程、UI |
| 增加协议命令 | XSYD 命令定义和业务翻译 | 传输、UI |
| 更换协议 | 新协议适配器 | 会话、领域、UI |
| 更换 WebHID | 新 `DeviceTransport` | 协议业务、应用用例 |
| 增加旋钮等控件 | 新地址类型或现有 `IndexedAddress`、UI 几何 | 公共键位模型 |

## 已消除的主要风险

- UI 不直接访问 WebHID 或拼接协议字节。
- 协议矩阵地址与页面视觉坐标分离。
- 键码表、布局和设备能力均通过驱动注入。
- 设备默认键位通过 `DefaultKeymapResolver` 注入，协议层不再引用具体型号。
- 键盘视觉几何由组合根注入通用画布，组件不再绑定 C98。
- Store 通过工厂接收应用服务，响应式状态与操作编排已拆为独立文件。
- 设置面板样式已从全局覆盖文件迁移到独立 UI 模块，后续样式按相同方式继续收敛。
- 命令规格与请求队列、业务解析分离。
- 保存流程具有校验、差异写入、提交、回读验证和进度事件。
- 配置比较不依赖设备回读顺序。
- 关闭会话会拒绝排队命令并释放浏览器监听器。
- 依赖边界、CRC、布局、能力、保存事务和命令生命周期均有自动测试。

## 不应凭猜测继续优化的部分

### 精确物理布局

C98 的完整矩阵地址到视觉坐标映射需要未省略的六行矩阵数据或固件布局表。仅凭默认键码推断位置，在重复键码、空矩阵位和不同语言配列下不可靠。

### 自动重试

读取命令通常可以重试，写入、保存和恢复出厂是否幂等必须由协议确认。未确认前自动重试可能造成重复写入或设备状态不确定。

### 响应关联

当前协议没有已确认的请求序号，客户端只能串行执行并按响应命令字关联。超时后的迟到响应是否会与下一条同命令请求混淆，需要真机时序测试或固件增加事务标识。

### 真正的固件能力查询

能力描述器已经提供版本分支位置，但最终规则需要不同固件样机或固件能力命令作为事实来源。

## 当前停止结论

在不增加新需求、完整协议证据或真机测试结果的前提下，继续增加抽象层的收益已经很低。下一阶段重点应从“重构”转为“协议证据和硬件验证”：补全矩阵样本、确认命令幂等性、覆盖断连和迟到响应、验证旧固件能力。获得新证据后，再针对具体问题演进，而不是预先设计万能框架。
